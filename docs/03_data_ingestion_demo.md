# Получение данных

На втором этапе подключены данные заказов, производственный календарь и погода. Для проверки загрузки взят период с 01.09.2024 по 31.08.2026 и 30 товаров.

## Источники

**Заказы и остатки.** Доступа к реальному кабинету продавца нет, поэтому используется генератор. Он создаёт отдельные файлы за каждый день. В заказах есть товар, количество, цена, скидка, статус заказа и оплаты. В остатках — запас на начало и конец дня, а также ожидаемые поступления.

В генераторе предусмотрены сезонность, акции и дни, когда товара нет в наличии. При одинаковых дате и seed результат повторяется. Это нужно для проверки повторной загрузки. Движение запасов между днями и изменение статусов старых заказов пока не моделируются.

**Календарь isDayOff.** Загружается по API за целый год. Ответ содержит по одному коду на каждый день: рабочий, выходной, сокращённый или праздничный. Календарь нужен, чтобы проверить, отличаются ли продажи в рабочие и нерабочие дни.

**Погода Open-Meteo.** Для Москвы загружаются температура, осадки и код погоды. Исторические данные берутся из ERA5, а прогноз на семь дней сохраняется отдельно. Влияние погоды на продажи пока не проверено — это задача следующего этапа.

Даты, число товаров, seed и координаты указаны в `configs/sources.json`. Используется московский часовой пояс.

## Как запустить

Нужен Python 3.11 или новее. Дополнительные пакеты устанавливать не надо. Команды выполняются из папки `marketplace-demand-forecast`.

```powershell
python -X utf8 -m src.ingestion.demo
```

Скрипт делает три запуска:

1. Загружает данные за два года.
2. Повторяет загрузку за тот же период. Уже загруженные заказы и погода пропускаются, календарь берётся из кэша. Дубли появляться не должны.
3. Добавляет 01.09.2026. Загружается только новый день: заказы, 30 снимков остатков и одна строка погоды.

Отчёт находится в `reports/generated/data_sources_demo.html`. Его можно открыть в браузере. Рядом сохраняется JSON с результатами запусков. Если данные уже есть в базе, повторный запуск их пропустит — результаты первой загрузки приведены в [04_deadline_2_results.md](04_deadline_2_results.md).

Для обычной загрузки или добавления дня:

```powershell
python -X utf8 -m src.ingestion.pipeline
python -X utf8 -m src.ingestion.pipeline --end 2026-09-02
```

История ERA5 публикуется с задержкой, поэтому дата окончания должна быть хотя бы на 6 дней раньше текущей даты.

## Показ без интернета

После сетевой загрузки ответы API остаются в `data/raw`. Можно повторить показ по этим файлам в отдельной базе:

```powershell
python -X utf8 -m src.ingestion.demo --offline --raw-dir data/raw --data-dir data/interim/replay-01 --report-dir reports/generated/replay-01
```

Для следующего показа с пустой базой надо указать новое имя папки, например `replay-02`. В отчёте будет отмечено, что использовался кэш. Если текущая дата изменилась, сначала нужно получить новый прогноз погоды через интернет.

## Где лежат данные

| Путь | Содержание |
| --- | --- |
| `data/raw/synthetic/` | Дневные файлы заказов и остатков в JSONL |
| `data/raw/isdayoff/` | Ответы календарного API |
| `data/raw/open_meteo_history/` | Ответы с исторической погодой |
| `data/raw/open_meteo_forecast/` | Ответы с прогнозом погоды |
| `data/interim/sources.sqlite` | База SQLite |
| `data/interim/*.csv` | Выгрузки данных и журнал загрузок |
| `data/processed/daily_demand.csv` | Количество оплаченных и неотменённых единиц по товару и дню |

Рядом с ответами API сохраняются адрес запроса, время получения и контрольная сумма файла. Новые ответы также сохраняются в `snapshots`, чтобы при обновлении не потерять предыдущую версию прогноза.

В базе записи разделены по источнику. Для заказов используется ключ из номера заказа и позиции, для остатков — дата, склад и товар. Календарь хранится по дате, погода — по дате и региону. У прогноза дополнительно учитывается время получения.

Журнал содержит время запуска, источник, период, количество полученных и добавленных строк, статус и ошибку, если она возникла. При ошибке изменения по этому источнику отменяются. Для сетевых запросов предусмотрены таймаут 30 секунд и до трёх попыток. Если сохранился некорректный ответ, получить данные заново можно с параметром `--refresh`.

## Проверки и ограничения

Проверяются уникальность ключей, статусы заказов, цены, количества и остатки. Для календаря проверяется число дней в году, для погоды — даты, пропуски, единицы измерения и коды условий.

```powershell
python -X utf8 -m unittest discover -s tests -v
```

Синтетические продажи позволяют проверить загрузку, но по ним нельзя судить о точности на реальном маркетплейсе. Нулевой остаток отмечается отдельно: в такой день продажи могли быть ограничены запасом.

ERA5 — реанализ, то есть сочетание наблюдений и модельных оценок. Текущий прогноз погоды нельзя использовать как прогноз, известный в прошлом. При построении модели нужно учитывать время его получения, в том числе при расчёте на 06:00 МСК.

Для демонстрации достаточно показать три запуска, пример исходного файла и журнал. После этого можно объяснить, что при повторе число записей не изменилось, а новый день добавился отдельно.

Документация: [isDayOff](https://www.isdayoff.ru/docs/), [историческая погода](https://open-meteo.com/en/docs/historical-weather-api), [прогноз погоды](https://open-meteo.com/en/docs). Погодные данные — Open-Meteo, ERA5 / Copernicus C3S, лицензия CC BY 4.0.

Данные и автоматически созданные отчёты не включаются в Git. В репозитории остаются код, настройки и описание запуска.
